# P5-J8 · 可观测与运维手册（单机多实例）

> 2026-11-25 · 公开运行手册；不含密钥、题库原文、个人数据。
> 详细切片、阈值判定过程与原始证据在内部（`docs/private/p5/j8/`，不随仓库）。
> 配套：[HA 演练手册](HA-演练.md) · [P5 §9](../p5/P5-Java业务.md)

## 1. 边界

- **单机多实例**，不是生产监控、不是多可用区；观测栈独立 compose（`docker-compose.obs.yml`），
  不占 HA 应用栈 8 GB 业务预算。
- **告警阈值是 demo 尺度**（与本机 J7 压测环境一致），不是生产建议；生产口径见每条 runbook 的调整方向。
- Jaeger 用**内存存储**（重启丢）；不承诺长期 trace 留存。
- nginx / Qdrant 是单点；PG 主从是手动提升，RPO 不承诺 0。
- 不引入 Loki：日志是结构化 JSON，查询走 `docker compose logs`；接入 Loki 是后续可选项。

## 2. 拓扑与入口

| 组件 | 地址 | 说明 |
| --- | --- | --- |
| Prometheus | `http://127.0.0.1:9090` | 15s 抓取、7 天保留 |
| Alertmanager | `http://127.0.0.1:9093` | 分组 / 抑制 / 静默 |
| Grafana | `http://127.0.0.1:3001` | 匿名 viewer；admin 密码由 `GRAFANA_ADMIN_PASSWORD` 注入（默认仅本机 demo） |
| Jaeger | `http://127.0.0.1:16686` | 内存存储（J8-B） |
| Alert sink | `docker/volumes/obs/alerts/alerts.jsonl` | Alertmanager webhook 落盘（机械证据） |

抓取目标：`gateway-1/2:8080`、`business-1/2:8081`、`worker-1/2:8081`、`api-1/2:8000`，
以及 postgres / redis / kafka / nginx / cadvisor exporter（全部走 `marda-ha-net` 容器 DNS）。

指标端点口径：Java `/actuator/prometheus`、Python `/metrics`，**仅容器网络可达**；
nginx 不路由 `/actuator` 与 `/metrics`。

## 3. 启动 / 停止

```bash
# 前置：HA 已起，网络 marda-ha-net 存在
docker compose -f docker-compose.obs.yml up -d
docker compose -f docker-compose.obs.yml ps

# 停止（保留数据卷）
docker compose -f docker-compose.obs.yml down

# 重载 Prometheus 配置（rules / scrape）
curl -X POST http://127.0.0.1:9090/-/reload
```

Grafana 看板与 datasource 由 provisioning 自动加载（`docker/obs/grafana/`），
改 JSON 后 30s 内自动刷新（provider `updateIntervalSeconds`）。

## 4. 看板

| 看板 | 回答的问题 |
| --- | --- |
| `Marda · 总览与 SLO` | 可用性、错误预算 burn rate、请求率、5xx、p95 |
| `Marda · 学习闭环与事件` | 面试开始/完成、计划/任务/通知、缓存命中、outbox 积压、Kafka lag |
| `Marda · 资源与中间件` | 容器 CPU/内存、PG 连接/复制延迟/库大小、Redis、nginx、Kafka |
| `Marda · LLM 槽位与成本` | 槽等待 p95、断路器、调用结果；成本跳 Langfuse |

## 5. 告警与 runbook

> 分组：`alertname + cluster`；抑制：`RedisDown` 时不再重复报 `CacheHitRatioLow`。
> 通知落点：Alertmanager → `alert-sink`（JSONL）。恢复后 Alertmanager 会发 resolved。

### HighErrorRate

**症状**：gateway / business 的 5xx 比例 > 1% 持续 5 分钟。

**确认**：
```bash
curl -sG http://127.0.0.1:9090/api/v1/query \
  --data-urlencode 'query=job:http_5xx_ratio:5m'
docker compose -f docker-compose.ha.yml logs --tail=50 gateway-1 business-1
```

**处置**：先看是网关（`502/504` 下游不可达）还是 business（`5xx` 业务异常）；
网关问题看 business readiness 与熔断状态；business 问题看 `ApiExceptionHandler` 日志与 PG / Redis。
必要时摘流（`bash scripts/ha/drain.sh gateway-1`）或回滚（J9）。

**恢复判据**：5xx 比例回到 < 0.1% 且告警 resolved。

**生产调整**：把阈值改为按 SLO（99.9%）推导，不使用 demo 的 1%。

### HighLatencyP95

**症状**：business p95 > 100 ms 持续 5 分钟（J7 校准口径，500 RPS）。

**确认**：
```bash
curl -sG http://127.0.0.1:9090/api/v1/query \
  --data-urlencode 'query=job:http_latency_p95:5m'
```
看 Hikari pending、Redis 慢日志、PG `pg_stat_activity`。

**处置**：按 J7 调优清单（连接池 / 缓存 / 舱壁）；demo 先确认不是压测机 CPU 竞争。

**恢复判据**：p95 回到 100 ms 以下，且 burn rate < 1。

### KafkaConsumerLagHigh

**症状**：`sum(kafka_consumergroup_lag) > 10000` 持续 5 分钟。

**确认**：
```bash
docker exec marda-ha-kafka-1 /opt/kafka/bin/kafka-consumer-groups.sh \
  --bootstrap-server 127.0.0.1:9092 --describe --all-groups | head -30
docker compose -f docker-compose.ha.yml ps worker-1 worker-2
```

**处置**：看 worker 是否存活、是否在 rebalance；查毒消息（DLQ 重放脚本 `backend/scripts/replay_dlq.py`）；
Kafka 故障时 outbox 会积压，broker 恢复后自动补发（J5 语义）。

**恢复判据**：lag 回落到 < 1000 并持续下降。

### OutboxBacklog

**症状**：`sum(marda_outbox_pending) > 1000` 持续 5 分钟（agent outbox 未发布）。

**确认**：
```bash
docker compose -f docker-compose.ha.yml ps relay-1 relay-2
curl -sG http://127.0.0.1:9090/api/v1/query \
  --data-urlencode 'query=sum(marda_outbox_pending)'
docker compose -f docker-compose.ha.yml logs --tail=50 relay-1
```

**处置**：relay 挂了 → 起 relay；Kafka 挂了 → 先恢复 broker（outbox 不丢，恢复后补发）。
`business_outbox` 积压看 `marda_business_outbox_pending`（worker 侧）。

**恢复判据**：pending 回落，relay 日志出现 published 批次。

### RedisDown

**症状**：`redis_up{job="redis"} == 0`（Redis 本身不可达）或 `up{job="redis"} == 0`
（exporter 不可达）持续 30s。前者是真正的缓存/锁依赖故障，后者只是指标断档。

**确认**：
```bash
curl -s http://127.0.0.1:9121/metrics | grep '^redis_up'
docker exec marda-ha-sentinel-1 redis-cli -p 26379 SENTINEL get-master-addr-by-name marda-master
docker compose -f docker-compose.ha.yml ps redis-master redis-replica-1 redis-replica-2
```

**处置**：缓存 **fail open**（回源 DB）、锁 **fail closed**（开新场次 503）、限流 fail open。
若 Sentinel 已切换，按 J6 规程重指应用与 exporter（`REDIS_HOST` 可能仍指向旧 master）。

**恢复判据**：`up{job="redis"} == 1`；缓存命中率回升；开新场次恢复 200。

### ReplicationLagHigh

**症状**：`max(marda_pg_replication_lag_seconds) > 10` 持续 5 分钟。

**确认**：
```bash
docker exec marda-ha-postgres-primary-1 psql -U marda -d marda -c \
  "select client_addr, state, replay_lag from pg_stat_replication;"
```

**处置**：查网络 / 从库负载；读仍走主库（J6 不做应用层读写分离）。
长时间不恢复要评估是否提升（`scripts/ha/promote_pg.sh`，RPO 不承诺 0）。

**恢复判据**：replay_lag < 1s。

### CacheHitRatioLow

**症状**：business 缓存命中率 < 80% 持续 10 分钟。

**确认**：
```bash
curl -sG http://127.0.0.1:9090/api/v1/query \
  --data-urlencode 'query=marda:cache_hit_ratio:5m'
```
查 TTL / key 前缀 / 是否有批量冷启动；`X-Cache: BYPASS` 表示 Redis 故障回源。

**处置**：先排除 Redis 故障（见 RedisDown）；冷启动会自然恢复；不要为了命中率调大 TTL 掩盖穿透。

**注意**：business 重启后缓存冷、流量又低时，这条会在 10 分钟后触发——先预热再判断，
demo 阈值不区分"冷启动"与"穿透"。

**恢复判据**：命中率回到 > 90%（J4 / J7 基线 93.5%）。

### LlmQueueHigh

**症状**：`marda_llm_slot_wait_seconds` p95 > 30s 持续 5 分钟。

**确认**：
- 看板 `Marda · LLM 槽位与成本` 的按 tier 曲线；
- `LLM_SLOTS_FLASH` / `LLM_SLOTS_PRO`（Redis 全局槽）与 `LLM_MAX_CONCURRENCY_*`（本地闸门）不要混；
- 上游是否限流 / 断路器是否开路。

**处置**：按 J7-T3 调整全局槽（32 是本机 50 并发下的可用值）；或降级到 flash。
不要只加本地闸门——Redis 模式下全局槽才是主限制。

**恢复判据**：p95 < 3s（J7 基线 2.49s @ 32 槽）。

### TargetDown

**症状**：某个 scrape target `up == 0` 持续 2 分钟。

**确认**：
```bash
curl -s http://127.0.0.1:9090/api/v1/targets | jq \
  '.data.activeTargets[] | select(.health!="up") | {job:.labels.job, instance:.labels.instance, err:.lastError}'
```

**处置**：容器是否在、端口是否变、指标端点是否被鉴权拦截（应为内网放行）。
`business` 的 `/actuator/prometheus` 若 403，检查 `ServiceTokenFilter` 的 permit-paths；
`gateway` 若 401，检查 `SecurityConfig` 的放行范围。

### CheckpointGrowthHigh

**症状**：`marda_pg_database_size_bytes{datname="marda_checkpoints"} > 5GB`（demo 阈值）。

**确认**：
```bash
cd backend && .venv/bin/python scripts/checkpoint_stats.py --help
```
看张数 / 字节 / 压缩比；保留策略默认每场最近 20 张 + 最终一张（`CHECKPOINT_RETENTION`）。

**处置**：确认保留策略在 finalize 后执行；需要立即清理时跑
`backend/scripts/checkpoint_retention.py`（先 `--dry-run`）。**不做**定时 retention（J8 范围外）。

**恢复判据**：库大小回落或增长速率趋稳。

## 8. 已知边界

| 项 | 边界 | 处理 |
| --- | --- | --- |
| Redis Sentinel 切换 | exporter 仍连旧 master，指标可能断档或角色错 | 切换后重指 `redis-master`（与 J6 应用重指同口径）；演练时如实记录 |
| PG 手动提升 | exporter / 应用都指向旧主库 | 按 J6 规程 `PG_HOST=postgres-replica` 重建应用；exporter 同理 |
| cAdvisor（macOS） | Docker Desktop 上只有 cgroup `id` 标签，没有容器名 `name` 标签 | 看板用 `id=~"/docker/.+"` 汇总口径（总 CPU / 总内存）；容器级细分退化，不假装有 |
| 单文件 bind mount | 编辑器 truncate+write 时容器可能读到截断配置（Prometheus 报 YAML unexpected end of stream） | 观测栈的配置一律按目录挂载（`docker/obs/*` → `/etc/...`） |
| Jaeger | 内存存储，重启丢；tail sampling 的 `decision_wait=90s`，trace 结束后约 1.5 分钟才出现在 Jaeger（长轮次需要这个窗口，5s 会拆分 trace） | 只用于排障；不承诺长期留存 |
| 抓取目标 | Prometheus 覆盖 core + agent + events 三类 profile；只起 core 时 api / worker target 会 down（TargetDown 告警），属预期 | 观测栈按全量 HA 验收；只跑 core 时忽略这两组 TargetDown |
| 告警阈值 | demo 尺度 | 生产按 SLO / 容量模型重算，不直接沿用 |
| 日志查询 | 不引 Loki | `docker compose logs` 与 JSON 字段（request_id / trace_id） |
| gateway 访问日志的 trace_id | WebFlux 的 WebFilter 在 server span 外层，拿不到 span（`Tracer.currentSpan()` / MDC / Reactor context 均为空） | 网关用 `request_id` 与 business / api 日志串联；trace 看 Jaeger；不为此手写 traceparent（会与 OTel 冲突） |
| 成本 | Langfuse 已有 | Prometheus 不重复采集 token；Grafana 放链接 |
