## 1. 一句话

P5 不是“把 Python 换成 Java”，而是把 Marda 的产品闭环从**面试诊断**延伸到**学习执行**：
让报告里的短板变成可执行、可提醒、可追踪的学习计划，并用 Java 业务服务 + 轻量网关 + 异步事件
把这套新业务做稳。

## 2. 用户问题：诊断结束，治疗没开始

Marda 现在能完成一条完整的诊断链：

`模拟面试 → 五维报告 → 短板定位 → 学习推荐`

但用户拿到建议之后，产品没有接住下一步：

- 不知道**下一步做什么**、每天做多少、先做哪个；
- 没有提醒和追踪，**难以坚持**；
- 看不到自己的进步，能力档案里只有“面试分数”，没有“学习行为”；
- 结果是一次面试结束，报告被读完就结束；用户容易流失，下一场面试也缺少新的个性化输入。

一个具体的用户旅程：

1. 候选人完成一场 Agent 面试，报告指出“RAG 检索”是短板；
2. 页面推荐了三个学习方向；
3. 用户关掉页面——没有计划、没有提醒、没有完成记录；
4. 一周后回来，档案仍然只有面试分数；下一场面试官仍按同样的方式出题。

**诊断是清楚的，治疗是断掉的。** 这是 P5 要补的产品缺口。

## 3. 业务目标：把“一次面试”变成“持续学习”

目标闭环：

`模拟面试 → 五维报告 → 短板定位 → 个性化学习计划 → 今日任务 → 到点提醒 → 完成/跳过 → 能力档案回写 → 下一场面试的推荐与出题`

| 环节 | 现在 | P5 之后 |
| --- | --- | --- |
| 面试 | 完整 | 不变 |
| 报告 / 短板 | 完整 | 不变 |
| 学习执行 | 只有推荐卡片 | 计划 / 任务 / 提醒 / 完成度 |
| 能力档案 | 面试五维分数 | 增加“学习行为”维度 |
| 下一场面试 | 从头开始 | 读取学习进展，影响推荐与出题 |

关键设计取向：

- **计划从报告来**：不是通用课表，而是从本场短板与目标岗位生成；截止时间 / 优先级来自计划配置；
- **任务可执行**：有截止时间、优先级、状态（todo / in_progress / done / skipped）；
- **提醒可关闭**：尊重用户偏好（渠道、免打扰时段、时区）；
- **完成度会回写**：学习行为进入能力档案，成为下一场面试的输入；
- **面试仍是验证点**：下一场面试既验证学习效果，也产生新的短板，形成闭环。

业务价值：

- **用户侧**：知道下一步、能坚持、看得到进步；
- **产品侧**：从“一次性工具”走向“持续学习闭环”，目标是提升次月留存、下一场面试转化与口碑；
- **数据侧**：能力档案多一维“学习行为”，推荐与出题不再只看面试分数。

> 当前是单机 demo，没有真实用户留存 / 转化数据；以上是**产品目标与后续验证口径**，不是已验证结果。
> 本文以“学习计划 / 通知”为默认 Java 新域；最终选型在 J3 确认，
> 备选（题库运营后台 / 通知中心）见 [P5-Java业务](P5-Java业务.md) §12。

## 4. 为什么是现在

- P4 已把多 worker、PostgreSQL、Redis、checkpoint 治理、可靠性与降级链做稳，面试核心闭环完整；
- 下一阶段的增长点不是“再加一个面试功能”，而是**让用户把报告用起来**；
- 学习计划 / 通知是全新数据域，与 Agent 实时链路解耦，适合独立演进、独立降级；
- 现在做，可以在**不改面试主链路**的前提下，验证“诊断 → 执行 → 回写”的闭环。

换句话说：P4 解决的是“面试这条链路能不能稳”，P5 解决的是“面试之后用户还愿不愿意回来”。

## 5. 为什么是 Java + 轻量网关 + Redis + Kafka

每个组件都对应一个业务问题，不是为了堆技术：

| 组件 | 承接的业务问题 | 更简单的替代 | 为什么不用更简单的 | 失败语义 |
| --- | --- | --- | --- | --- |
| **Java 业务服务** | 学习计划 / 通知：有状态、调度、重试、审计；与 Agent 解耦 | Python 直接实现 | 新域需要独立部署、事务边界、调度与审计；但**不重写 Agent** | 学习计划不可用 → 空态；面试不受影响 |
| **轻量网关** | 统一鉴权、限流、路由、熔断、灰度、trace | nginx 路由 | JWT 校验、用户级限流、灰度权重、统一 trace 需要应用层网关 | 网关故障 → 业务 API 503；面试流不受影响 |
| **Redis** | 读多写少的热点数据（题库分面、报告摘要、能力档案、今日任务）+ 限流 / 锁 | 本地缓存 | 多实例需要共享缓存；本地缓存只做二级 | 缓存故障 → 回源 DB；锁 fail closed、限流 fail open |
| **Kafka + outbox** | 报告完成 → 建计划 / 发通知异步化；削峰、重试、重放、审计 | 同步调用 / Redis 队列 | 同步调用会把“报告收尾”和“学习计划”绑死；Redis 队列不适合长期事件与重放 | Kafka 故障 → outbox 积压；面试不受影响 |

**边界（同样重要）**：

- **SSE / WebSocket 不走 Java 网关**，面试流仍是 nginx → Python 直连；
- **Java 不放进面试关键路径**；学习计划故障时降级为空态，面试照常；
- **不做分布式事务**：outbox + 幂等 + 最终一致；
- **不做分库分表**：数据量不支撑，先做容量模型；
- **不引入第二个 MQ / 配置中心 / 注册中心**：Compose DNS + 环境变量足够；
- **不把 P5 做成技术栈演示**：每个组件必须有业务问题、失败语义和证据。

## 6. 成功标准

### 业务指标（目标 / 验证口径）

| 指标 | 说明 |
| --- | --- |
| 报告 → 计划创建成功率 | 报告完成后自动创建计划成功的比例（失败可重试） |
| 7 日任务完成率 | 计划是否真的被执行，而不是“生成了但没人做” |
| 通知送达率 / 打开率 | 提醒是否有效，是否打扰 |
| 下一场面试转化 | 学习之后是否愿意再面一场 |
| 次月留存 | 是否从“一次性工具”变成“持续学习” |
| 档案覆盖率 | 有多少用户的能力档案包含学习行为 |

### 工程指标（与 [P5-Java业务](P5-Java业务.md) §1.6 一致，J7 校准）

- 业务 API：p95 < 100ms @ 500 RPS；
- 缓存命中率 > 90%；
- MQ 通知：端到端 p95 < 5s、零丢失、DLQ < 0.1%；
- 故障演练与回滚通过；
- HA profile 总内存 < 8GB。

> 这些是**验收目标**，不是当前实测。J0 的 before 数字见内部 J0 记录；
> SLO 在 J7 压测后校准。

## 7. 工程动机与边界

P5 也有工程能力建设的考虑：在真实业务域里补齐 Spring 业务、Redis / Kafka、网关治理、
压测与故障演练。但这是**业务目标的副产物**，不是做 P5 的理由——如果新业务域不成立，
这些技术选择也不成立。

同样明确不做什么：

- **不重写 Python Agent**：LangGraph 图 + 工具 + 状态机是一个整体，拆开只会增加序列化和一致性成本；
- **不为了用 Java 而用 Java**：存量业务不迁；Java 只承接全新业务域与轻量网关；
- **不承诺未验证的留存 / 转化数字**：只写目标与验收口径；
- **不做通用学习平台**：只服务 Marda 的“面试 → 学习 → 再面试”闭环；
- **不把单机多实例表述为多可用区高可用**：边界写清楚，证据按边界给。
